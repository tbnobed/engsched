TBN PLEX ENGINEERING · API V1

Tickets and technician schedules

Integrate from your application’s backend using an API key. Base path: /api/v1 on this application’s host. Use HTTPS outside local development.

Manage API keys (admin) · Download OpenAPI specification

Authentication and permissions

Create a key under Admin → API Access. Save it securely when shown: the full key cannot be retrieved later. Read and write scopes are separate and apply to all tickets or schedules, not just records assigned to the key owner. Directory scope exposes user names and email addresses.

Authorization: Bearer YOUR_API_KEY
Content-Type: application/json

X-API-Key: YOUR_API_KEY is also supported. Login cookies and keys in URLs do not authenticate API requests. Never put a key in public frontend code. Cross-origin browser access is not enabled; use your backend. Expired/revoked keys and keys whose owner was deleted or lost admin access return 401.

Examples

Replace https://YOUR_APP_HOST with your application’s actual host, and load PLEX_API_KEY from your server’s secret manager. These examples never require a password or session cookie.

curl "https://YOUR_APP_HOST/api/v1/tickets?status=open&page_size=50" \
  -H "Authorization: Bearer $PLEX_API_KEY"

curl "https://YOUR_APP_HOST/api/v1/tickets" \
  -H "Authorization: Bearer $PLEX_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: source-system-event-123" \
  -d '{"title":"Studio monitor issue","description":"No signal on monitor 2.","category_id":1,"priority":2}'

curl "https://YOUR_APP_HOST/api/v1/schedules?technician_id=1&start=2026-10-01T00:00:00Z&end=2026-11-01T00:00:00Z" \
  -H "Authorization: Bearer $PLEX_API_KEY"

curl "https://YOUR_APP_HOST/api/v1/schedules" \
  -H "Authorization: Bearer $PLEX_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: source-booking-456" \
  -d '{"technician_id":1,"start_time":"2026-11-03T09:00:00-08:00","end_time":"2026-11-03T10:00:00-08:00","description":"Studio maintenance"}'

Look up actual IDs in /technicians, /categories and /locations; the example IDs are placeholders.

Integration rules

  • JSON envelopes: single records use {"data": {...}}. Lists use {"data": [...], "meta": {"page":1,"page_size":50,"total":12,"pages":1}}. Lists are ordered by ID, with up to 100 rows per page. Pagination is live, not a frozen snapshot.
  • 120 requests per minute per key, shared across server workers. Respect 429 and Retry-After. Responses include X-Request-ID; authenticated responses also include rate-limit headers.
  • JSON request bodies are limited to 256 KiB. PATCH updates only supplied fields; unknown fields and invalid types are rejected. Send null to clear nullable fields, not an empty string.
  • Use an Idempotency-Key on POST to prevent duplicates after retries. Keys are scoped to one API key, replay successful requests for 24 hours and cannot be reused for a different path/payload. Rotating an API key starts a new idempotency namespace. PATCH/DELETE do not accept this header.
  • API writes record history/audit entries but do not send email, run AI, or automatically cancel other bookings. A posted comment is recorded, not emailed to the requester. Internal notes appear in ticket history.
  • Ticket DELETE archives rather than destroys; use PATCH {"archived":false} to restore. Schedule DELETE permanently removes that one entry. API v1 does not upload/download attachments or mutate recurring templates.
  • Dates require ISO 8601 offsets. Responses use UTC; display in the technician/user timezone. Schedule windows use half-open overlap: entry.end > start and entry.start < end. Adjacent entries are allowed, overlapping entries return 409 without changing existing appointments.
  • All-day entries require time_off:true and midnight start/end boundaries in the technician’s profile timezone, with an exclusive end (the following midnight for one day). Schedule entries are limited to 366 days. Weekly templates describe patterns; they do not represent automatically generated future bookings.
  • Input descriptions/comments are plain text. HTML response fields reflect existing rich text and must be sanitized before rendering in another application.

Errors and retries

{"error":{"code":403,"message":"Required permission: tickets:read."},"request_id":"..."}

400 means invalid input; 401 means invalid credentials; 403 means a missing scope; 404 means the record/path was not found; 405 means the method is unsupported; 409 means a scheduling or idempotency conflict. Retry 429 after its specified delay; retry transient 500 errors with backoff and the same POST idempotency key. Do not automatically retry validation or permission failures.
